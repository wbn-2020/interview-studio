## 1. 已采用的内容决定

1. **B01／P01是PRD v0.4首期的两套种子，本文保留完整自检样例，AI评价规格另见AI体验设计。**两套先用于合成内容讨论；未审标准只能作探索性检查方向，不自动认证技术正确。自建题可贴入并记来源，标准可空，私用不自动公开。约12题为试用后扩充目标；末尾10个方向和AI预览中的简化情景都不是已完成专家审核的题包，也不是20–30例质量集。
2. **B01 有确定配置下的接收推演，但没有跨配置的万能答案。**固定 Java 21、空池、串行提交及任务不完成，逐个推演 1–7；同时单列并发、关闭、队列及线程条件变化。
3. **P01 没有唯一架构答案。**先守住本人责任、未知结果、可证明的结果确认与重试条件；查单、获准回调、对账和人工处理可以是不同合理路径。
4. **自检是用户操作，不是自动阅卷。**清单提供条件与候选判断；用户选择原文或声明“未提及”，确认一个缺口，再接受、争议或忽略动作。不按关键词、篇幅、术语数量或流畅度判对。
5. **引用只证明可定位，不证明判断正确。**公开 JDK URL 只支持所列 JDK 规格；不能据此证明项目发奖契约、用户经历、产品效果或内容已获复核。未使用商业题库或第三方题目正文。

### 1.1 每套样例的使用顺序

- 作答前：显示题干v1、目标、条件和责任；本稿案例采用自检模式，AI训练／短模拟的角色与时机按AI体验规格，标准仍标未审。
- 作答时：专项可按需展开三层提示并记录阶段，不扣分；短模拟进行中不显示提示／参考／纠错，不能将本稿自检顺序套用于模拟。
- 提交后：保留原答修订，再展开参考标准与自检；一条反馈须绑定题干、标准、事实和被检查的回答版本。
- 复练时：保留原动作与来源，另建独立新尝试；显示条件、标准、事实和提示使用是否变化。
- 对照时：由用户记录“已处理／部分／未处理／无法判断”，并指出新答依据。提交新答、复制参考或更长的回答都不自动结项。
- 本文的新答只是**允许示例**，不替用户作答，也不能被保存成用户本人独立生成的答案或真实经历。

| 不在本题内认证 | 编码与运行能力、生产调参经验、所有竞态细节、口头临场能力、整个并发专题已掌握 |

题干中可见的条件包 `B01.C.v1`：

| 条件 ID | 固定条件 |
|---|---|
| C1 | 普通 `ThreadPoolExecutor` 正在运行，`corePoolSize = 2`，`maximumPoolSize = 4`。开始时池中 0 个 worker、队列为空；不预启动核心线程。 |
| C2 | 工作队列为容量 2 的 `ArrayBlockingQueue<Runnable>`，拒绝处理器为 `AbortPolicy`。 |
| C3 | 一个提交线程依次调用 `execute(T1)` 至 `execute(T7)`，上一次调用返回后才提交下一任务；任务均非 null，没有其他提交者。 |
| C4 | 到达期间任务不完成、不取消；已获得任务的 worker 一直被该任务占用，不取后续队列任务。线程创建成功，worker 不异常退出，无额外资源异常。 |
| C5 | 提交期间没有关闭、参数修改、外部队列取放或额外钩子行为。核心线程不超时退出；本题没有空闲退出事件。 |

这里的 worker 数不是 `getActiveCount()` 的瞬时结果。创建 worker 并交给任务，不等于保证 `run()` 已在某个观测时刻开始。

### 2.2 题干 v1

> 在条件包 `B01.C.v1` 下，向池依次提交 T1–T7。请逐个说明每个任务交给新 worker、进入队列还是被拒绝，并给出每步的 worker 数和队列数。解释任务 T3、T5、T7 为什么走不同路径。
>
> 请区分“接收去向”与任务实际开始／完成次序；若要把结论用于并发提交、关闭或另一种队列，先说明哪些条件需要重新判断。

这是一个主问题，不自动追加追问。可用表格、编号列表、状态图或简短口述，不要求固定模板。

### 2.3 参考标准 v1

**适用范围：**仅针对 `B01.C.v1`。依据公开 JDK 21 `ThreadPoolExecutor` 的 core/max、Queuing、Rejected tasks 和相应方法说明；不是源代码逐行证明或实测结果。

接收策略的技术含义：

1. 池中 worker 少于 core 时，优先创建 worker 承接新任务，即使已有 worker 空闲也不是先入队。比较的是池线程数量，不是“当前忙线程数”。
2. 至少达到 core 时，优先尝试将新任务入队，而不是先扩到 max。
3. 队列无法接收时，再尝试创建 worker，不能超过 max；本题线程创建成功。
4. 本题队列不能接收且 worker 已达 max 时，任务交给 `AbortPolicy`，该策略抛出 `RejectedExecutionException`。

逐步参考推演：

| 任务 | 接收时关键状态 | 接收去向 | 本步后 worker 数 | 本步后队列内容／数量 |
|---|---|---|---:|---|
| T1 | 0 < core 2 | 新建 W1 承接 T1 | 1 | 空／0 |
| T2 | 1 < core 2 | 新建 W2 承接 T2 | 2 | 空／0 |
| T3 | 已达 core，队列有空位 | 入队 | 2 | T3／1 |
| T4 | 已达 core，队列还有 1 个空位 | 入队 | 2 | T3、T4／2 |
| T5 | 队列满，2 < max 4 | 新建 W3 承接 T5 | 3 | T3、T4／2 |
| T6 | 队列满，3 < max 4 | 新建 W4 承接 T6 | 4 | T3、T4／2 |
| T7 | 队列满，worker 已达 max | `AbortPolicy` 抛拒绝异常给提交方 | 4 | T3、T4／2 |

- 六个任务被池接收，T7 未被池接收。T7 不是静默丢弃，也不是由 `AbortPolicy` 在提交线程中运行。
- W1、W2、W3、W4 是推演别名，不是产品观测到的线程 ID。表中的“本步后”是这些假设下的接收状态，不是对几次统计读取作出的原子快照承诺。
- T5、T6 不必排在 T3、T4 后开始。队列 FIFO 约束队列元素的先入先出，不约束全池开始／完成顺序；本题到达期间没有完成事件。
- `ArrayBlockingQueue.offer(E)` 满时返回 false，不会因满而等待空位；`put(E)` 的等待语义不能套到此接收策略。也不因此承诺 `execute` 的耗时上界或任何情况下绝不等待。
- “达到 core”不等于“先把线程数扩到 max”。“被拒绝”也不等于“所有已接收任务停止”。

#### 条件变化：哪些结论不再可直接套用

| 改变的条件 | 可以据规格说什么 | 不能沿用什么 |
|---|---|---|
| 多线程并发提交 | 以实际竞争时的状态判断接收，不可把编号当串行到达顺序；统计值和打印先后不是完整接收证据 | 本题 T1–T7 的逐行归属、开始先后；不能凭某个瞬时读数复原全过程 |
| 有任务在到达期间完成 | worker 可能消费队列，空位与线程状态变化 | 固定的 T3、T4 一直留在队列，以及 T7 必然因饱和被拒绝的推演 |
| 提交前已 `shutdown()` | 不接受新任务，先前提交的任务按有序关闭语义处理；在本题 `AbortPolicy` 下新任务被拒绝时抛异常 | “只要队列有空位就能接收”；不能说 `shutdown()` 等于立即杀掉全部任务 |
| `execute` 与关闭并发 | 需要承认接收与关闭之间的竞态；官方 API 给高层契约，不给完整精确判定算法 | “看到运行中就必接收”“入队一度成功就必执行”，或把特定 OpenJDK 的重检／移除步骤说成本文已证明的 API 契约 |
| `shutdownNow()` | 尝试中断执行中的任务，停止处理并返回等待任务；终止是尽力而为，不保证忽略中断的任务停止 | 原“没有关闭且任务持续占用”的条件，以及立即全部终止的保证 |
| 改成默认 `new LinkedBlockingQueue<>()` | 在相同空池和这 7 个任务的假设下：T1、T2 承接于新 worker，T3–T7 入队；不因这些入队触发超过 core 的扩容 | “无界队列也会先扩到 max”。默认容量是 `Integer.MAX_VALUE`，不是数学无限；不能承诺永不拒绝、永不积压或没有内存风险 |
| 改成 `SynchronousQueue` | 不存储任务，直接交接失败会促使尝试建 worker；若保持空池、任务占用且无法即时交接，本题前 4 个可由 worker 承接，后续因上限拒绝 | 容量 2 的排队表；不能把直接交接当成普通缓冲队列 |
| 预启动核心线程或允许空闲核心线程超时 | 初始 worker 数、空闲 worker 与提交时状态需重新确认；超时需满足相应 keep-alive 条件 | 从 0 个 worker 起算的每步路径；不因“空闲”就把 worker 当不存在 |
| 线程创建失败、worker 退出或参数变化 | 本题的成功创建与稳定参数前提失效。官方文档讨论工厂返回 null 时可能无法执行任务，但不保证每次失败都走同一种结局 | 六个接收／一个拒绝的确定推演，或“创建失败一定立刻拒绝”的泛化 |
| 换拒绝策略 | 重新查看 handler 契约；如 `CallerRunsPolicy` 在未关闭时可由提交线程运行被拒任务 | T7 的异常结论。若 T7 在提交线程运行且也不完成，串行提交方会被占住，不可把它当背景执行后继续套表 |

`getPoolSize()` 返回当前池线程数，文档没有把它标为近似值；但单次读数不说明整个并发过程。`getActiveCount()` 明确是近似活跃数。不得把两者混同或凭其认定特定任务已经开始／完成。

### 2.5 合成原答与可允许的新答

**合成原答 `B01.A0.v1`**，只用于设计选段与自检：

- `p1`：先扩到4个线程，再入队。
- `p2`：第7个丢弃，不抛异常。
- `p3` 的 JSON 字符串如下；解码后作为一段短原文，仅用于 emoji 范围测试，不作为技术能力证据。

```json

```

**可允许的新答 `B01.A1.v1`**，与原答分离保存：

- `p1`：按题干的空池、串行提交、任务不结束和创建成功条件判断。
- `p2`：T1、T2 各交新 worker；T3、T4 入队；T5、T6 因队列满增加 worker，最终为4个；T7 抛拒绝异常，队列仍是 T3、T4。
- `p3`：达到 core 后先入队，不先扩满。这里判断的是接收去向，不保证开始顺序；并发、关闭或换队列要重新判断。

**另一种允许表达 `B01.A1-alt.v1`**：

> 条件按题干。去向依次为：新 worker、新 worker、队列、队列、新 worker、新 worker、异常拒绝。最终 worker 为4、排队为2。第3个有队列空位，第5个才扩容，第7个无容量。FIFO 不代表全池执行顺序。

### 3.7 合理替代路径与禁止结论

| 合理路径 | 成立条件／仍需补证据 | 不强制的形式 |

**禁止结论：**

- “超时就是失败”“查不到就是没发”“换个号重试最安全”“只要有请求号就保证幂等”。
- 用 U1 认定接口已经幂等或绝对不幂等；认定用户一定重复发奖、一定造成损失或不懂幂等。
- 把参与了解升级为本人实现，替用户补造上线成果、吞吐量、损失金额、事故复盘或职责。
- 仅因超时释放预算，或承诺能无限冻结／任意延期外部预算；将发奖幂等推广成跨系统 exactly-once。
- 将查询与回调冲突按最后到达覆盖，或强制某种锁／组件作为唯一合理答案。
- 因原答没有回调就判错；因有“查单”关键词就认定已说明确认路径；因新答长或谨慎就认证安全。
- 把本文合成事实确认成真实经历，把方案建议视为已实现；把 JDK URL 当发奖契约或业务成果证明。

## 4. 两套样例的 code point 定位夹具

这些夹具属于 B01、P01 原答中的短段，**不是额外题目，不参与技术评分**。下面均为人工推导的测试预期，尚未运行。emoji 以转义展示，需解码后计数；可以选普通中文片段，不必要求用户选中 emoji 本身。

| `B01.A0.v1/p3`：`"我先\uD83E\uDDEA重答。"` | 6 code points；7 code units | `"\uD83E\uDDEA"` | `[2,3)` | `[2,4)` |

设计检查动作与判断条件：

1. **正例**：绑定原版本和段落，按表中范围选取“重答／查单”，片段完全匹配才算定位有效。
2. **计数混用反例**：直接把 B01 的 `[2,3)` 当 UTF-16 范围会切开 surrogate pair；不能通过 code point 范围校验，也不能补猜为整个 emoji。
3. **片段不匹配反例**：P01 使用 `[5,7)` 却声明片段“查单”，实际为“先查”，必须拒绝该引用；全文相似不构成通过。
4. **越界／版本反例**：P01 的 `[0,10)` 超过 9 code points；或拿新答版本定位旧答，均拒绝有效引用并说明原因。
5. **缺失来源**：原文删除或不可访问时显示“来源已删除／不可访问”，不能在当前版本搜索相似句补位置。
