# 知识关系候选与逐项采用契约

版本：v1.8 · 2026-11-10。适用 S5 第十五批、第二十一至二十八批关系候选及证据边界；各批实际状态与证据以[开发记录](../开发记录/开发阶段与进度.md)为准。承接 PRD KNOW-06／07、AI-02–06 及[正式关系规则](首阶段接口与数据契约.md)、[AI 外发契约](AI任务与外发契约.md)；本契约不证明运行或视觉验收通过。

## 1. 流程与边界

用户选择 2–5 个本人 ACTIVE、当前已发布知识版本，其中至少两个 CONCEPT，NOTE 可作依据 → 阅读完整外发清单与费用 → 本次授权 → 核对关系候选、引用与限制 → 修改类型、方向或理由 → 逐条采用或忽略。候选保存在 AI 任务，第二十三批可由用户按需投影到[星图待审层](知识关系候选星图契约.md)，不进入正式关系、路径或计数；不能因为主题共属、词频共现或为了图谱连通而自动建边。没有足够依据时允许返回零条候选，成功不等于必须生成关系。

原纯知识入口不自动展开关联笔记、主题、现有关系、准备材料或训练记录；只有所选知识的六字段 Source 与完整要求外发。当前版本检查沿用知识来源规则，草稿编辑不替换固定发布正文；来源改版或当前归档时阻止新发送、接纳和采用。收藏、主题及布局不改变发布版本。第二十二批的[手工直接原文证据](正式关系直接原文证据契约.md)、第二十四批的[自检／外部反馈证据](正式关系反馈原文证据契约.md)和第二十五批的[AI 反馈选区证据](正式关系AI反馈原文证据契约.md)分别保存，不构成模型外发授权。第二十六批以[资料／训练来源关系候选](资料训练来源关系候选契约.md)的独立预览入口增加明确选择的直接输入，第二十七批增加[人工反馈／面后回忆关系候选](人工反馈与面后回忆关系候选契约.md)，第二十八批增加[AI反馈生成关系候选](AI反馈生成关系候选契约.md)；完整间接更正仍待后续。

## 2. 输入与模型结果

原纯知识用途 RELATION_DRAFT 使用提示版本 `relation-draft-1`，sources 仅 NOTE／CONCEPT，其余用途专属输入均为 null。要求最多 1000 UTF-16 码元，无 NUL／孤立代理；来源身份唯一、标题及正文有效，端点概念正文不得为空白。外发预算使用与网关一致的 `{purpose,instruction,sources}`，沿用 32 KiB、输出和费用限制，不截断正文。两种协议继续走既有传输与 usage 恢复。

第二十六批沿同一用途新增 `relation-evidence-draft-1`：Manifest 尾加 nullable `relationEvidence`，仅旧值为 null 时从摘要投影省略，以保持历史 hash；其他用途拒非空混入。新清单包含完整知识与一个 MATERIAL／TRAINING 输入，新指令保留首尾空白；每条候选新增两个直接引用数组，对应来源至少一条，知识引用可为零，三类引用合计1–6。旧候选新增数组缺省／null兼容；详情和原键回执比较仅规范化这些可空尾字段，完整内容仍需一致。新解析、V52绑定、预算与实际外发规则集中在专项契约，后文仅讲原知识结果格式的条款不扩用于新模式。

第二十七批沿同一用途新增 `relation-review-draft-1`：复用 reviewDraft 与 V43，选择当前人工反馈修订或 ACTIVE 回忆版本的1–8段，完整必要限定、当时决定与基线参与外发；relationEvidence 必须为 null。每项模型对象为六字段，持久对象为九字段，materialCitations／trainingCitations=null，reviewCitations 至少一条，与知识引用合计1–6。知识来源与 V43 固定身份在全生命周期核对；旧两种模式只接受 reviewCitations 缺省／null，完整指纹仅在非null时追加该尾字段。完整背景不授权引用未选区间，具体规则以专项契约为准。

第二十八批新增 `relation-ai-feedback-draft-1`，Manifest第24项 relationAiFeedback 与 reviewDraft／relationEvidence 互斥，固定成功评价单条反馈的18字段Snapshot。模型六字段、持久九字段，复用reviewCitations形状但按Snapshot专用规则检查，不能将AI反馈转换成人工Input；每项至少一条选区引文，与知识引用合计1–6。AI_UNREVIEWED、原报告字节摘要、成功尝试、必要限定和当时决定保持；完整历史限定可含NUL原样JSON转义，新片段、生成文本和引文禁NUL。新来源与原知识台账全生命周期核对，原键恢复先核固定答案访问；清单新空尾保持旧摘要兼容。

模型只返回 `{summary,limitations,relations}`：summary 非空、最多 1000 UTF-16；limitations 非空、最多 2000；relations 为 0–10 项。每项严格为 `{sourceItemId,targetItemId,type,reason,citations}`，id 由服务端按顺序赋予 r1–r10。端点必须是清单中两个不同 CONCEPT；type 限 PRECEDES、PART_OF、APPLIED_IN、RELATED、CONTRASTS。reason 非空、最多 1000 UTF-16。所有文本拒绝 NUL／孤立代理和未知字段。

PRECEDES 表示源是目标的前置知识；PART_OF 表示源是目标的组成部分；APPLIED_IN 表示源应用于目标；RELATED／CONTRASTS 无方向且按 UUID 字典序归一。候选按规范化端点＋类型去重；不同类型可并存。每项 1–6 条 Citation，合计不超过 60 条；引用只落到选定的完整 Source.body，沿用逐字、UTF-16 半开区间、代理对及去重规则。结构与定位通过不证明关系语义正确或被引用原文充分支持。

服务端补充 `RelationCandidate={summary,limitations,relations,validationNote}`；relations 元素为 RelationSuggestion（上述字段加 id）。不可变模型原候选与人工最终内容分别保留。其他用途的 relationCandidate／relationDecisions 必须 null；旧 JSON 缺尾字段按 null 兼容，不重写历史摘要。

## 3. 逐项决定与正式关系

Task 尾新增可空 relationCandidate 和 relationDecisions；RELATION_DRAFT 的 relationDecisions 为列表，其余用途为 null。每个候选最多一个终态决定 ADOPTED／IGNORED，单项命令包含 expectedRevision，成功增加任务修订及通知，但生成任务状态仍为 SUCCEEDED。没有“一键全采用”或借用旧整任务 ignore；决定后不再重试生成，原键恢复不重复决定。

采用内容为 `{sourceItemId,targetItemId,type,reason}`。两端必须与原候选相同或互换，不允许换成第三个概念；类型和理由可编辑，长度与方向规则同上。采用需显式 confirmed=true，任务成功、该项未决定、全清单来源当前有效；模型关闭不妨碍本地采用。忽略使用 ChangeTask，不要求来源当前，不写关系、不退款。

同一 owner 锁与命令事务中核对任务修订／来源、调用知识领域新建关系入口、写决定及人工最终内容、更新 AI 修订／通知、保存回执。复用正式关系的 ACTIVE CONCEPT、自环、对称去重、同类型 PRECEDES／PART_OF 无环及容量规则；归档节点的既有边仍参与闭环检查。若同端点／类型关系已经存在，AI 采用返回 409 RELATION_EXISTS，不给已有手工边补写 AI 来源，不保存决定；用户可调整或忽略。旧手工与画布创建仍保持复用已有关系的行为。

第二十一批通过[正式关系补充理由与来源契约](正式关系补充理由与来源契约.md)接入完整产品需求 §6.2 的独立补充流程：用户明确核对既有关系后，保存追加记录及一次候选决定，保留原关系身份、初始出处及每次补充。原新建采用的重复冲突保持；不会自动补充或覆盖旧出处。第二十二批接入资料／训练手工直接证据；第二十三批提供候选星图层，第二十四／二十五批分别追加人工反馈及 AI 反馈原文证据。第二十六至二十八批沿同一逐项决定流程，补充时核全部知识及相应直接、复盘或AI反馈来源；补充台账保存知识版本与原任务回链，其他输入由原任务及 V52／V43／V53 保留。回忆手工关系证据及间接更正等余项继续保留，不能据此将 KNOW-06／07 全部关闭。

[V27](../../backend/src/main/resources/db/migration/V27__ai_relation_candidates.sql) 扩展 ai_task 用途 CHECK，并增加独立 `ai_relation_source` 与 `ai_relation_decision`。来源在创建任务时保存 owner、task、对象、确切版本、顺序和当时元数据，使用 owner 复合外键。决定按 owner＋task＋candidateId 唯一，ADOPTED 保存关系 ID 与最终内容，IGNORED 对应字段为空。关系 ID 不建立指向可物理删除关系的外键；删除正式边后，原候选、决定和确切来源仍保留，原键回放不会重建边。来源查询双向核对关系记录与原清单，不以数据库故障冒充普通来源失效。

## 4. 接口与界面

所有接口受会话、owner 和独立训练资料守卫；命令要求 CSRF、Idempotency-Key。请求严格字段／类型，安全整数与 UUID 检查沿既有规则。

| 路径（前缀 /api/v1/ai） | 请求／响应 |
|---|---|
| POST /relation-drafts/preview | RelationDraftPreviewRequest `{instruction,sources}` → Preview |
| POST /relation-drafts/tasks | CreateRelationDraft（预览字段＋expectedManifestHash、consentConfirmed）→ Task |
| POST /tasks/{id}/relations/{candidateId}/adopt | AdoptRelation `{expectedRevision,content,confirmed}` → Task |
| POST /tasks/{id}/relations/{candidateId}/ignore | ChangeTask `{expectedRevision}` → Task |
| GET /relations/{relationId}/origin | RelationOrigin 或 null；包含原候选、最终决定、全部确切来源及 relationExists |

RelationDecision 原有 `{candidateId,status,relationId,content,createdAt}`；第二十一批尾加可空 `supplementId`，旧缺省按 null 兼容。新建与忽略为空，显式补充采用为独立补充 ID。RelationOrigin 基础字段为 `{taskId,candidate,decision,sources,relationExists}`，第二十六批尾加 nullable `relationEvidence`／`relationEvidenceState`，第二十七批再加 nullable `reviewDraft`／`reviewDraftState`，第二十八批再加 nullable `relationAiFeedback`／`relationAiFeedbackState`。显式展开相应模式会返回完整固定输入及来源状态，复盘及AI反馈模式先核当前访问；其他模式尾字段缺省／null兼容，不是仅元数据。AI反馈只用CURRENT／REVIEW_REQUIRED／UNAVAILABLE，不将报告或绑定损坏吞成状态。只读取 `supplementId=null` 的初始建边出处，后续补充在独立历史列表展示。知识来源使用原清单标题／版本与 CURRENT／SUPERSEDED／ARCHIVED／UNAVAILABLE 状态；正式边删除后仍能查询自身 owner 的历史决定。没有 AI 初始来源返回 null，不能把无来源解释成已验证的手工记录。

AI 工作区提供专用关系创建入口；候选显示两端、方向／类型、模型理由、引用与限制，逐项编辑／确认／忽略。查询更新保留人工改写，修订／清单变化撤销同意；未知结果保持原请求，迟到回执与会话／辅助守卫沿现有约定。采用成功刷新知识查询，新边由既有正式关系流程进入星图，不改节点布局。知识关系列表按用户展开加载来源并跳回原任务；不为每条关系自动批量查询。

第二十三批的 `GET /relation-drafts/tasks` 只读取成功关系任务摘要，第二十六至二十八批沿同目录，支持纯知识、知识加资料／训练、知识加人工反馈／回忆、知识加AI反馈四种输入模式；显式选择后，`GET /tasks/{id}/relation-graph` 返回未决定候选的窄投影。投影前严格核对固定清单、全部知识及相应输入、原候选和决定；复盘及AI反馈模式先核绑定与当前访问，保留原 rN。不返回清单正文、引文或 attempt 明细。引用数量仍为知识、材料、训练及复盘四类允许数组的合计，AI反馈复用review数组并专用校验，sourcesCurrent覆盖全部明确输入。目录分页、画布隔离及原20项场景以[候选星图契约](知识关系候选星图契约.md)为准，新模式分别保留RSD／RRV／RAI场景；原生成／采用接口和历史回执保持兼容。
