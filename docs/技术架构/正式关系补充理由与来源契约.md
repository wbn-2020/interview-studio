# 正式关系补充理由与来源契约

版本：v1.1 · 2026-11-09。适用 S5 第二十一批及第二十二批边界说明，状态：静态检查通过待服务器验收。承接 PRD KNOW-06／07、[正式关系规则](首阶段接口与数据契约.md)及[知识关系候选与逐项采用契约](知识关系候选与逐项采用契约.md)。实际进度以[开发记录](../开发记录/开发阶段与进度.md)为准，本契约 §8 保留第二十一批最终静态证据；编译与静态复核不表示接口、迁移或视觉验收通过。

## 1. 范围与关系身份

本批落实[产品需求](../需求文档/产品需求文档.md) §6.2 中同端点同类型关系的理由／来源补充：用户可向已有正式关系追加人工依据，也可将已审阅的 RELATION_DRAFT 单项候选及全部固定来源补充到明确选择的已有关系。每次补充形成独立、不可变记录；理由和来源通过原关系 ID 聚合展示，不覆盖既有理由、原始 AI 出处或此前补充。

`Relation={id,sourceId,targetId,type}` 保持原形状，不增加 revision。补充不修改关系 ID、端点或类型，不创建第二条边，不改变星图布局、关系计数或路径。PRECEDES、PART_OF、APPLIED_IN 保留方向；RELATED、CONTRASTS 按小写 UUID 字典序规范化端点。相同端点的不同类型仍是不同关系，自环始终无效。

原 `/adopt` 仍只负责新建关系；重复关系仍返回 `409 RELATION_EXISTS`，不自动改走补充、不保存该次候选决定。旧手工／画布创建接口的复用行为不因此改变。第十五批契约中“补充待实现”是该批历史范围，本批通过独立确认命令补齐此分支。

本批不增加 AI purpose，不改变 Manifest、外发清单、提示版本或清单 hash；补充命令不调用模型、不新增费用。AI 配置关闭不阻止有效历史候选的本地补充。第二十二批通过[独立直接原文证据台账](正式关系直接原文证据契约.md)接入手选资料摘录和确切回答片段，不扩充本契约的 RelationSupplement DTO 或 AI 决定；直接来源生成关系候选、反馈证据、候选星图图层及完整间接更正仍属后续工作，不能据此将 KNOW-06／07 全部关闭。

## 2. 补充内容与来源

### 2.1 人工补充

请求为 `{reason,sources,confirmed}`，所有字段必填且 `confirmed=true`。`sources` 为 0–5 项 `{itemId,versionId}`，允许只补理由；同一 itemId 不能重复。每个来源必须是本 owner 的 NOTE／CONCEPT，处于 ACTIVE，且 versionId 正好等于当前已发布版本。草稿正文、仅有新草稿的标题、旧版发布正文和未选对象均不代替所选版本。

首次提交时，原关系必须仍存在，两个概念端点均 ACTIVE。来源可以包含关系端点，也可以是其他当前知识版本；来源顺序按用户确认的数组保存。服务端从确切版本读取并保存 itemId、versionId、版本号、当时标题和 kind，不接受客户端指定这些版本元数据。

理由原样保存，不 trim、不拼接覆盖旧记录；有效长度为 1–1000 个 UTF-16 码元，拒绝 NUL、孤立代理以及全部由 `Character.isWhitespace` 或 `Character.isSpaceChar` 组成的内容。补充理由的新校验不追溯改写历史知识标题：标题继续保持原知识写入规则的兼容性，读取补充时按确切版本核对原值，不能用最新标题修补历史。

### 2.2 AI 候选补充

请求为 `{expectedRevision,relationId,content,confirmed}`，其中 `content={sourceItemId,targetItemId,type,reason}`。用户可调整原候选两端的方向、类型与理由，不能引入第三个概念；对称类型归一后，必须与明确指定 relationId 的实际端点和类型完全一致。只按端点匹配到另一条边不能替代用户已确认的关系身份。

任务必须为 SUCCEEDED 的 RELATION_DRAFT，candidateId 为该任务真实存在的 r1–r10，该项尚无终态决定，expectedRevision 与当前任务修订一致。expectedRevision 使用非负 JavaScript 安全整数。理由同时遵守本节严格文本规则。

来源固定为原 Manifest 的全部 2–5 项，数量、顺序、对象、版本及当时元数据必须与持久化任务来源逐项一致；用户不能只保留引用命中的来源，也不能用关系端点替换其余 NOTE。首次补充仍要求全部原清单来源当前 ACTIVE 且版本未变。来源已改版／归档时，即使未变化的端点仍可组成同一关系，也必须拒绝本次新补充。

## 3. HTTP 与对象契约

接口沿用会话、owner 隔离及既有访问守卫；命令要求 CSRF 与 `Idempotency-Key`。ID 为标准小写 UUID，owner 来自认证上下文。两个新增写接口从原始字节解析，拒绝重复 JSON 键、额外／缺失字段、尾随 JSON、错误类型和标量强制转换；请求体上限 262144 字节。不得将字符串布尔值、浮点修订号或数字 ID 当作合法输入。

| 操作 | 输入 | 响应与含义 |
|---|---|---|
| `GET /api/v1/knowledge/relations/match` | 查询参数 `sourceId,targetId,type` | `Relation` 或 JSON `null`；只匹配本人规范化端点＋类型，查询不创建边，也不承诺随后写入时仍有效。 |
| `GET /api/v1/knowledge/relations/{relationId}/supplements` | 可选 `cursor`、`limit`；limit 默认 20，范围 1–20 | `Page`；原边删除但本人历史仍存在时可读，`relationExists=false`。既无本人边又无本人历史则 404。 |
| `POST /api/v1/knowledge/relations/{relationId}/supplements` | `Create={reason,sources,confirmed}` | 201 `Supplement`；追加一条人工补充。 |
| `POST /api/v1/ai/tasks/{id}/relations/{candidateId}/supplement` | `SupplementRelation={expectedRevision,relationId,content,confirmed}` | `Task`；记录该项 ADOPTED 及 supplementId，返回新的任务修订。 |

对象形状以[共享 DTO](../../backend/src/main/java/com/wenjie/studio/knowledge/RelationSupplementDtos.java)及[AI DTO](../../backend/src/main/java/com/wenjie/studio/ai/AiDtos.java)为准：

| 对象 | 字段与约束 |
|---|---|
| `SourceLink` | `itemId,versionId`；仅用于提交身份，不携带客户端标题或状态。 |
| `Source` | `itemId,versionId,number,title,kind,state`；kind 为 NOTE／CONCEPT，元数据固定，state 反映读取时状态。 |
| `Supplement` | `id,relationId,sourceId,targetId,type,origin,reason,sources,taskId,candidateId,createdAt`。origin 为 MANUAL／AI；MANUAL 的 taskId、candidateId 均 null，AI 两者均必填。 |
| `Page` | `relationId,relationExists,items,nextCursor`。没有下一页时 nextCursor 为 null。 |
| `RelationDecision` | 原有 `candidateId,status,relationId,content,createdAt` 尾加可空 `supplementId`；原始新建与忽略均为 null，补充采用为该条补充 ID。旧 JSON 缺该尾字段按 null 兼容。 |

分页按补充 ID 的 UUID 字典序升序，条件为 `id > cursor`，不按 createdAt 排序。createdAt 单独展示，不能把页面顺序解释为发生时间。该游标不提供跨请求数据库快照；翻页期间新追加的 UUID 可能落在已读范围，重新加载列表可重新取得当前数据。单条补充内部的来源始终按原 ordinal 展示。

旧 `GET /api/v1/ai/relations/{relationId}/origin` 继续只返回“首次通过 AI 新建这条关系”的原始出处，查询必须限定 `supplement_id IS NULL`。人工创建后追加 AI 依据的关系，其原始 AI 出处仍为 null；AI 补充通过新历史列表与任务决定查看，不能冒充最初建边来源。

| 状况 | 契约结果 |
|---|---|
| 字段、理由、来源数量／重复项或确认无效 | 400 `INVALID_REQUEST`。 |
| 指定本人关系不存在且不能执行新补充 | 404 `RELATION_NOT_FOUND`；不按相同端点重建／改绑。 |
| 本次任务不存在该候选 | 404 `AI_RELATION_CANDIDATE_NOT_FOUND`。 |
| 首次补充时关系端点已归档 | 409 `RELATION_ENDPOINT_ARCHIVED`。 |
| AI 最终内容与指定关系的规范化身份不一致 | 409 `RELATION_CHANGED`。 |
| 人工或领域写入时来源不再是当前 ACTIVE 版本 | 409 `RELATION_SOURCE_CHANGED`；AI 原清单检查亦可能先按既有 AI 来源错误拒绝。 |
| 候选已决定／任务修订变化 | 409 `AI_CANDIDATE_DECIDED`／`REVISION_CONFLICT`；不追加记录。 |
| 同键改变操作或请求 | 409 `IDEMPOTENCY_KEY_REUSED`。 |

## 4. 事务、幂等与历史读取

人工补充在同一 owner 写锁及命令事务中复核原关系／来源，写台账与全部来源行，再保存回执。AI 补充还在该事务内核对任务／候选，写 ADOPTED 决定、最终人工内容和 supplementId，增加任务 revision，推进 AI 通知游标并保存回执；生成任务状态保持 SUCCEEDED。任何一步失败均回滚，不留下孤立来源、补充台账、候选决定或已提交通知。

原键同请求恢复返回原回执，不再次追加，也不重新要求边存在或来源当前。回执是命令完成时的快照，当前关系存在性与来源状态须重新查询列表／任务，不能把回执中的旧状态当作当前状态。会话、owner、通用命令访问守卫及适用的固定绑定检查仍执行，原键不能绕过权限。同键不同请求拒绝；AI 同项换新键后按已决定拒绝。人工补充没有“理由内容唯一”约束，用户明确发起的新键请求代表新的追加，因此未知结果必须保留原键和原请求恢复，不能自动换键。

正式边删除后补充台账及 AI 决定保留；列表返回 `relationExists=false`，原请求恢复不会重建边。同端点同类型重新创建后拥有新的 relationId，新边不继承旧 ID 的补充或原始出处。历史来源状态如下，状态变化不改写保存的理由、来源顺序及版本元数据：

| state | 读取含义 |
|---|---|
| CURRENT | 确切来源版本仍是 ACTIVE 知识的当前已发布版本。 |
| SUPERSEDED | 知识仍 ACTIVE，但当前发布版本已变；保留补充当时的旧版。 |
| ARCHIVED | 来源知识当前归档；即使 versionId 仍是当前版本也以归档状态显示。 |
| UNAVAILABLE | 读取时无法取得确切来源版本／对象；保留已存元数据，不代用其他对象。 |

正常数据库外键限制确切来源版本被删除；UNAVAILABLE 是读取兜底，不能据此跳过存储完整性检查。台账归属、规范化关系身份、AI 任务／候选绑定、来源数量、连续 ordinal、对象去重或原版本元数据不一致均属完整性错误，不能降级成普通来源失效。读取 AI 补充决定时还须逐项核对其不可变台账与原 Manifest；该核验不要求关系仍存在或来源仍当前。

## 5. V48 数据边界

[V48 迁移](../../backend/src/main/resources/db/migration/V48__relation_supplements.sql)增加 `knowledge_relation_supplement` 和 `knowledge_relation_supplement_source`。前者保存 owner、补充 ID、原 relationId、规范化端点／类型、origin、reason、source_count、AI task／candidate 与时间；后者保存 owner、supplementId、ordinal、确切知识／版本 ID、kind、版本号及标题。

台账不建立指向可删除正式边的外键。来源以 owner＋item＋version 复合外键绑定不可变知识版本，以 owner＋supplement 绑定台账；同补充的 source_item_id 唯一。数据库约束覆盖关系类型、对称归一、自环、来源数量／顺序范围、AI／MANUAL 条件字段及 AI 单候选唯一；来源行数量与连续顺序仍由领域写入和读取校验共同保证。理由的数据库字符长度 CHECK 不等同于 Java UTF-16／Unicode 校验，不能替代接口校验；来源标题不套用新增理由规则。

`ai_relation_decision` 新增可空 supplement_id 及生成列 original_relation_id：仅当 supplement_id 为 null 时，original_relation_id 取 relation_id，否则为 null。旧 `(owner_id,relation_id)` 唯一索引替换为 `(owner_id,original_relation_id)`，保留一个原始建边决定，同时允许多次不同候选的补充指向同一正式关系。原 `(owner_id,task_id,candidate_id)` 主键继续限制每候选一次终态决定；IGNORED 不可携带 supplement_id。

决定到台账的外键包含 owner、task、candidate、relationId、supplementId，防止决定引用另一候选或另一条边的补充。历史已采用记录的 supplement_id 默认为 null，继续参与原始出处唯一约束。本地未执行迁移；既有数据升级、生成列及外键在实际 MySQL 环境的生效情况均待服务器验收。

## 6. 已实现界面与恢复边界

以下说明依据最终源码静态核对，实际显示与交互仍待服务器验收。[知识关系列表](../../frontend/src/components/ConnectionsPanel.vue)在语义关系行接入[补充记录组件](../../frontend/src/components/RelationSupplements.vue)，用户展开后读取每页 20 条历史；显示人工／AI、理由、时间、确切版本标题与来源状态，支持前后翻页、刷新来源状态以及回到原 AI 任务。原边删除时展示保留历史的说明并禁止追加。来源不可用时保留文字，不提供失效对象跳转。

人工追加表单支持理由与 0–5 个来源。选择知识后再次读取详情核对 ACTIVE、当前发布版本及选择时版本号；只提交确切 itemId／versionId，不提交详情中的草稿或正文。修改理由／来源、刷新历史或访问条件变化均撤销旧确认；保存前独立勾选确认。页面将草稿和未决命令登记到离开保护，关闭表单或历史面板时经过未保存输入检查。既有 ItemEditor 的 `v-show` 保留关系面板实例；本批未修改 ItemEditor 或 main 入口。

[AI 逐项审阅组件](../../frontend/src/components/ai/AiRelationCandidates.vue)提供“新建正式关系”和“补充到已有关系”两种明确方式。补充方式按编辑后的规范化端点／类型查询，展示命中的 relationId、原补充历史及 Manifest 全部来源，独立确认后提交该关系身份。匹配未命中时显示说明，不自动创建；原 `/adopt` 的 RELATION_EXISTS 提示可引导用户主动切换补充方式。最终内容、任务／来源、访问条件或操作方式变化时清除匹配与确认，保留人工改稿。来源标题与历史关系文本按 Java 既有空白规则兼容，新补充理由使用更严格的 Unicode 空白规则。

人工成功回执须通过[补充响应校验](../../frontend/src/api/relationSupplement.ts)，核对原 relationId、origin、理由及来源身份／顺序后才清空表单；不匹配的回执保留原请求和键。AI 决定回执须核对任务、Manifest、不可变原候选、目标候选、最终内容及 supplementId，任务 revision 必须恰为发送时 revision＋1。返回决定集合须恰好新增目标一项，全部发送时已有决定保持一致，并与当前页面已知决定不冲突，之后才结束该项编辑和原请求。[任务详情](../../frontend/src/components/ai/AiTaskDetail.vue)按 candidateId 合并迟到决定，不回退其他终态决定。

网络结果未知时用原请求恢复；会话或资料访问条件变化后到达的回执暂缓接收，恢复访问后提供核对入口。成功后刷新相关知识查询或补充列表；失败、修订冲突与回执不匹配保留改稿。界面不自动把删边后重建的同元组关系替换为原选中身份，也不自动回退新建采用。以上回执与草稿保护已有静态证据，迟到响应、会话切换、键盘与窄屏等真实交互仍列入 RSU-20。
