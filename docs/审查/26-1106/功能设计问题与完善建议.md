## 1. 总体判断

**功能大类基本齐全，不完善的地方主要是：用户完成一步之后，系统如何归因、安排下一步，以及如何可信地结束追踪。**

本清单将原审查中的六个相关问题归为五类，不增加新的缺陷数量，也不把建议记为用户已确认的需求：

| 编号 | 功能设计问题 | 主要影响 | 原审查映射 | 优先收口时点 |
|---|---|---|---|---|
| FUNC-01 | 岗位具体要求与训练证据的对应规则不完整 | 不知道某次训练支持哪条要求，可能过宽判断覆盖 | AUD-07 · P2 | S5 评价／S6 复盘与 S7 成长衔接前 |
| FUNC-02 | 已采用复练动作缺少“不再追踪”的出口 | 悬挂动作积压，容易误用“已处理”清空列表 | AUD-08 · P2 | S6 动作与复练实施前 |
| FUNC-03 | 共享任务多截止日期与改期冲突规则不完整 | 多场面试准备可能错误后移或重复安排 | AUD-09 · P2 | S7 今日计划与面试安排集成前 |

## 2. 五类功能设计问题

### FUNC-01 · 岗位要求 → 题目 → 作答证据的映射不完整

**已有设计**

- 支持多个目标、JD 和具体要求，要求已有版本身份。
- 题目有解释、排错、取舍、职责、表达等通用考察维度。
- 成长页按目标／主题／考察项汇集证据，跨目标复用需检查场景、技术版本、辅助条件和时间。
- 不以一次回答直接认证整体岗位能力。

**仍需补齐**

1. 哪道题、哪项反馈或哪次回答，对应目标的哪一条具体要求？
2. 适用关联由用户确认、系统建议还是内容预设，如何区分？
3. 通用维度匹配到具体要求时，哪些能支持、哪些尚未覆盖？
4. JD 改版后，旧关联如何保留，新要求是否需要重新确认？

**典型场景**

JD 同时要求“缓存故障恢复”和“数据库锁等待排查”，两者都属于排错。用户只练过数据库锁题，不能因此把缓存要求也显示为已有覆盖。

**建议完善**

- 通用维度继续用于检索和选题；目标归因使用确切的要求身份及版本。
- 保存题目／回答／反馈与要求之间的适用说明，区分用户确认和建议关联。
- 没有可靠关联时显示“未关联／待确认”，不默认覆盖。
- 目标页展示相关证据、适用范围和未覆盖内容；“有证据”不等于“已掌握”。
- JD 改版保留旧关联，不静默将旧成果升级为新要求的证据。
- 普通练一题不增加必填映射表单；仅在目标归因或准备规划中按需关联。

**功能验收场景（待服务器执行）**

- 建立两条同维度要求，只关联其中一条；另一条仍没有对应证据。
- 修改 JD，旧训练能打开原要求，新要求不自动继承覆盖。
- 无目标训练仍可完成，不强制补 JD 或要求映射。

依据：[主报告 AUD-07](产品审查报告.md)、PRD 的 PRE-02／GROW-01–03、[准备契约](../../技术架构/准备与资料接口与数据契约.md)与[题库契约](../../技术架构/题库与学习路线接口与数据契约.md)。

### FUNC-02 · 已采用动作缺少可信的退出追踪路径

**已有设计**

- 反馈可以接受、争议或忽略；采用后可以形成带验证条件的动作。
- 一个动作可合并多个来源，各来源分别判断结果。
- 延期、暂停、移出今日不会冒充完成；取消安排也不会取消动作。

**仍需补齐**

用户采用动作后，可能核实原反馈不适用、改变目标，或决定不再投入时间。此时既不应一直待处理，也不应通过“已处理”虚构一次复练成功。

**典型场景**

用户采用“补充缓存双写方案”的改进动作，后来确认该反馈不适用于当时题目。取消今日安排后动作仍悬挂；标记已处理又没有实际验证依据。

**建议完善**

- 为动作来源提供显式“归档／不再追踪”入口，并记录原因。
- 不再追踪不等于已处理，不增加复练完成数，不形成成长提升结论。
- 多来源动作只退出所选来源，其他有效来源继续保留。
- 保留原反馈、用户决定和已有复练记录；恢复追踪须显式操作，不重置历史。
- 暂停追踪、取消安排、不再追踪、复练处理分别命名，避免共用一个“完成”按钮。

**功能验收场景（待服务器执行）**

- 合并动作包含 A／B 两个来源，仅退出 A：A 不再推荐，B 保持有效。
- 退出不改变原反馈、不增加完成统计；恢复 A 后历史仍可查。
- 取消今日安排只影响安排，不冒充退出动作或完成验证。

依据：[主报告 AUD-08](产品审查报告.md)、PRD 的 DAY-02／REV-04–05／RET-04–05及第9节、[架构生命周期](../../技术架构/系统架构与数据边界.md)。

### FUNC-03 · 多场面试共用准备任务时，期限与改期规则不完整

**已有设计**

- 今日、日历和动作列表共用任务身份，重复加入不复制任务。
- 改期先预览未开始的影响，已完成记录不移动。
- 用户锁定日期受到保护；当前 S3 仅修改面试安排和提醒，准备任务随后续阶段集成。
- 时间预算超出时已有显示剩余、允许编辑的要求，不是缺少预算功能。

**仍需补齐**

1. 同一任务服务多个目标／面试时，哪个截止日期生效？
2. 某场面试延期、取消或移除关联后，如何重新判断？
3. 自动建议与用户锁定日期冲突时，移动还是提示？
4. 多期限与时间预算冲突，如何说明任务未被安排的原因？

**典型场景**

缓存复练同时服务周二和周五的面试。周二延期到下周，不能把共享任务一并移到周五之后，也不能复制一份破坏身份去重。

**建议完善**

- 自动安排建议参考最早有效截止日期；用户锁定日期优先，冲突只提示、不强制搬动。
- 改期预览展示所有期限来源、有效日期变化及未移动原因。
- 取消一场面试只移除其期限约束，不关闭底层动作。
- 沿用已有时间预算与剩余规则，解释哪些到期任务暂未进入今日；调整建议不修改历史完成记录。
- 同一任务只保留一个身份，按多个来源判断，不靠复制解决冲突。

**功能验收场景（待服务器执行）**

- 两场面试共用一任务，延期较早场后仍只有一个任务，期限受另一场约束。
- 取消一场不关闭动作；手工锁定日期和已完成记录保持不变。
- 可用时间不足时能查看剩余任务和建议理由，不显示全部已安排。

依据：[主报告 AUD-09](产品审查报告.md)、PRD 的 DAY-03–04／PRE-04／EVENT-02、[附件与安排契约](../../技术架构/附件与安排接口与数据契约.md)。

### FUNC-04 · 回忆自评、延期与排程需要明确区分

#### A. 评级必须描述揭示前是否成功回想

**已有设计：**先想／写再揭示、自评与浏览／跳过分离、事件与排程共同保存；自评不代表技术审核或岗位能力。

**残留问题：**主规格的“困难／熟悉”可能被理解成没想起来但眼熟。既有调研已建议更明确文案，尚需对齐主规格及算法映射。

**建议评级含义：**

| 文案 | 用户应依据的回忆情况 |
|---|---|
| 忘记 | 揭示前未能回想成功 |
| 费力想起 | 已成功回想，但明显困难 |
| 正常想起 | 已成功回想，有少量犹豫 |
| 轻松想起 | 已成功回想且轻松 |

“看答案后眼熟”不算成功回想。由用户选择等级，系统不猜测其是否记住；开放题的记忆自评也不证明技术正确。

#### B. 延期不能隐含复习完成或重新起算

**已有设计：**移出今日不抹到期，暂停排除队列，恢复显式启用，历史事件不重写，允许明确排程方式的人工日期。

**残留问题：**“延期”可能被实现成暂缓展示、人工改日期或重新计算间隔，含义仍未统一；积压时新卡、常规旧卡和同日学习／重学的呈现顺序也需说明。

**建议区分：**

| 操作／日期 | 应表达的含义 |
|---|---|
| 算法到期 | 根据真实复习事件和策略得到的建议时间 |
| 队列暂缓 | 暂时不进入今日呈现，不改写原到期依据 |
| 人工改期 | 用户明确覆盖安排日期，记录原因和排程方式 |
| 暂停／恢复 | 控制是否进入队列，不生成一次成功复习 |
| 真实复习 | 按实际发生时间记录评级，再计算下一次建议 |

预算限制呈现与建议数量，不让剩余到期项消失。积压时的新卡策略和同日学习／重学优先级应明示，允许查看剩余；不以未经验证的记忆概率解释结果。

**功能验收场景（待服务器执行）**

- 揭示前未想起、揭示后眼熟时，解释仍明确应按失败回想自评。
- 浏览、跳过、延期和暂停均不增加成功复习记录。
- 分别执行队列暂缓与人工改期，能查看不同日期来源及原因。
- 预算耗尽仍能查看剩余到期项，真实复习按实际时刻排程。

依据：[主报告 AUD-10／11](产品审查报告.md)、PRD 的 MEM-02–07及第9节、[复习调研](../../调研/知识管理与复习调研.md)与[算法适配选型](../../技术架构/技术选型与决策.md)。

### FUNC-05 · 白板要形成可靠的保存、恢复与交换能力

**已有设计**

- 卡片引用源对象，一个笔记可在多个画布出现，移出实例不删源正文。
- 图面位置、组织和历史属于视图；画布线不自动成为知识语义关系。
- 保存和历史有版本冲突保护，外部格式允许支持子集和损失提示。

**仍需补齐**

- 交互规格允许调尺寸，但当前 BoardNode 持久契约没有宽高，难以表达每个实例的尺寸历史。
- 导入／导出需要字段级映射：尺寸、箭头、文件片段、分组等哪些保留，哪些降级。
- 普通内部 JSON 下载、兼容 `.canvas` 交换和完整知识备份应分别命名，不能互相冒充。

**典型场景**

同一代码笔记在两块白板中使用不同宽度，用户需要各自保存、刷新和撤销；导入另一工具的画布时，还需要知道箭头或分组是否会损失。未运行页面，本清单不声称已经发生布局丢失。

**建议完善**

- 将宽高纳入视图实例及历史，规定默认值和范围，不写入源笔记正文。
- 多实例分别保存尺寸，撤销只影响相应视图，不倒改训练提交快照。
- 交换预览列出“保留／明确默认／警告降级／跳过”，不只提示未知节点类型。
- 不支持项保留原包并可查，不能静默截断；画布箭头不推导概念前置关系。

**功能验收场景（待服务器执行）**

- 两个视图实例分别调整尺寸，保存、刷新、历史读取和撤销保持各自结果。
- 源正文修改仍同源更新，但不改变各视图独立布局或旧训练快照。
- 画布往返时支持字段一致，损失项逐项显示，不创建虚构语义边。

依据：[主报告 AUD-06](产品审查报告.md)、[交互规格](../../交互设计/知识星图与工作台.md)第3.1节、[知识工作区契约](../../技术架构/知识工作区接口与数据契约.md)第5节、PRD 第11.2节格式兼容目标。

## 5. 建议收口顺序

1. **先补全主业务链：**岗位要求 → 选题与独立作答 → 有依据的反馈 → 用户采用动作 → 空白复练 → 条件化对照 → 目标证据。
2. **S6／S7接入前收口：**FUNC-01～04的映射、退出、共享期限和排程语义，与对应契约共同修订。
3. **白板完善和交换前收口：**FUNC-05与保存方式，保证现有功能可持续使用，不靠新增画布补齐可靠性。
4. **用服务器证据验证：**低负担无材料路径、跨模块状态、真实模型质量、中文输入、窄屏／键盘／非拖动，以及完整数据恢复。

这只是依赖和风险优先建议，**不裁剪完整产品为MVP，不新增语音、社区、招聘或付费模型接入。**
